# Настройки входа (этап 1)

Реализованы локально. Не деплоить без подготовки нового секрета на VPS.
SSH, пользователь запуска, права кассира, денежные операции и фоновые
уведомления в этот этап не входят.

## Окружения

- `DJANGO_ENV=development` — локальная разработка по HTTP, отдельный ключ.
- `DJANGO_ENV=production` (по умолчанию) — HTTPS-only cookies, HTTPS redirect,
  DEBUG всегда False, конкретные домены. Не определять production по DEBUG.
- `DJANGO_SECRET_KEY` обязателен: случайный, не менее 50 символов, без insecure
  fallback. Сгенерировать на каждой машине отдельно через secrets.token_urlsafe(64).
- Никаких прежних известных ключей в SECRET_KEY_FALLBACKS. После смены ключа
  пользователи должны быть готовы войти заново. Данные и пароли не удаляются.
- `.env` не коммитить, права 0600. Локальную `.env` на VPS не копировать:
  она содержит development-профиль и другой ключ.
- `DJANGO_ALLOWED_HOSTS`: имена через запятую, без схемы/портов/wildcards.
  По умолчанию production dacar-market.kz,www.dacar-market.kz; local loopback,
  localhost и Android emulator. LAN-адрес Mac при необходимости добавить явно.
- `DJANGO_CSRF_TRUSTED_ORIGINS`: по умолчанию пусто — обычные same-origin формы
  работают. Добавлять только реальные альтернативные origins со схемой и портом.
  Туннели для разработки разрешать по конкретному имени, а не маской.

## Обязательная проверка proxy перед production

Gunicorn должен остаться привязан к 127.0.0.1. Nginx обязан ПЕРЕЗАПИСЫВАТЬ
`X-Forwarded-Proto` значением `$scheme`, `X-Real-IP` — `$remote_addr`.
`DJANGO_TRUSTED_PROXY_IPS` содержит только непосредственные доверенные proxy
(по умолчанию в production 127.0.0.1,::1, локально — пусто).
`X-Forwarded-For` для ограничения входа не используется. Без указанной настройки
proxy все клиенты могут попасть в один бюджет или подменять IP.
HTTPS-профиль рассчитан на текущий reverse proxy, не на открытый Gunicorn.
HSTS в этом этапе не включается, его предупреждение check --deploy ожидаемо.

## Ограничитель входа

- Один бюджет на `/users/login/`, `/m/users/login/` и `/admin/login/`.
- 5 попыток на комбинацию IP+нормализованный логин за окно 5 минут.
- 60 попыток на IP за окно 5 минут против перебора разных логинов.
  Этот общий аварийный предел всё же может ограничить общий IP магазина при
  массовых ошибках/атаке. Нормальные успешные входы возвращают свой IP-слот.
- Слот резервируется атомарно ДО хеширования пароля; успешный user_logged_in
  сбрасывает только пару и возвращает один IP-слот. Заблокированные запросы
  не продлевают окно. Уже авторизованные кассы не разлогиниваются.
- Нет глобальной блокировки аккаунта по всем IP: атакующий с чужого IP не
  может заблокировать этот логин для всех. Распределённый перебор через множество
  разных IP этот механизм полностью не устраняет — это не MFA/WAF.
- При превышении — 429 + Retry-After, при проблеме хранилища — 503, без
  пропуска защитной проверки. CSRF проверяется раньше ограничителя.
- Хранилище `runtime/security/login.sqlite3` отдельно от бизнес-БД, общее для
  Gunicorn workers. Каталог 0700, файл 0600. Нужна запись у пользователя сервиса.
  Нет Redis/Celery, фоновых потоков, shell-команд или записи паролей в журнал.
- Сохраняются только HMAC-ключи и счётчики, устаревшие строки удаляются при
  следующем POST. Максимум 10000 активных строк, затем fail-closed 503.
- Не запускать на файловой системе без корректных SQLite-блокировок (NFS).

## При выпуске

1. Согласовать время смены ключа/повторного входа пользователей.
2. Создать отдельный секрет VPS и выставить production в его окружении.
3. Проверить Nginx headers и локальный bind Gunicorn, доступ к runtime.
4. Выполнить check --deploy с production-настройками; затем перезагрузить сервис.
5. Проверить вход обычного сотрудника и суперпользователя, desktop/mobile/admin,
   Secure cookies, запрет чужого Host, возврат 429 после неудачных попыток на
   тестовом логине, не блокируя рабочие учётные записи.
6. Миграции для этого этапа не нужны. Широкие тесты с test_all_features.py
   не запускать. Целевые тесты: config.test_security_settings users.test_login_security.

Права, расчёты/возвраты/идемпотентность и круглосуточная история мониторинга
с уведомлениями реализованы локально. Перед production остаётся отдельный
операционный выпуск: секрет VPS, миграция `sales.0006`, collectstatic,
перезапуск Gunicorn и установка systemd timer мониторинга. Этапы
backup/PostgreSQL, смена root и SSH исключены по запросу пользователя.
