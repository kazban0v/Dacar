# Мониторинг в Django Admin

Раздел `/admin/monitor/`, JSON `/admin/monitor/data/`. Доступ только активному
суперпользователю с доступом в admin; существующие регистрации моделей, CRUD,
права и последние действия сохранены. Никаких управляющих команд или SSH.

## Локально

Установить зависимости из requirements.txt, запустить Django обычным способом.
Миграции для мониторинга не нужны. На Mac показывается локальная машина, не VPS.
`MONITOR_LABEL` в окружении задаёт подпись машины (например, DACAR VPS).
Расположение отдельного хранилища — `settings.MONITOR_DB_PATH`.
По умолчанию `runtime/monitor/metrics.sqlite3` (игнорируется Git), каталог 0700,
новый файл 0600. Никогда не публиковать runtime через Nginx/static/media.

## Нагрузка и измерения

- psutil читает счётчики ОС без sleep, shell, обхода процессов и каталогов.
- Один общий снимок в 10 секунд на все Gunicorn workers; собственная SQLite
  сериализует сбор. Чтение актуального снимка не берёт write lock.
- История: не более 1440 точек, один первый снимок в минуту за 24 часа.
  Это точечные наблюдения, не максимум/среднее каждой минуты.
- CPU и сеть считаются по разнице сохранённых счётчиков. Первый замер после
  старта/перезагрузки/паузы свыше 120 секунд — неизвестен, а не ложный ноль.
- Сеть суммируется по интерфейсам без lo/lo0; это не только HTTP-трафик,
  виртуальные интерфейсы могут учитывать один пакет несколько раз.
- RAM percent и available получены из psutil; available учитывает освобождаемый
  кэш. Диск — файловая система каталога проекта, не сумма всех накопителей.
- Единственный запрос в рабочую БД — SELECT 1. Не проверяет целостность,
  продажи, резервные копии или внешнюю доступность сайта.
- Браузер получает свежий снимок раз в 10 секунд, историю раз в минуту.
  Скрытая вкладка и ручная пауза останавливают запросы. Графики — локальный canvas.
- Никакие background threads не создаются внутри Gunicorn/runserver.

## Непрерывная история и тревоги (для DevOps)

Без сборщика история растёт только при открытом разделе; пробелы на графике
сохраняются. Для круглосуточной истории подключите готовые unit-файлы
`deploy/systemd/dacar-monitor.service` и `dacar-monitor.timer`, затем:

```sh
/var/www/dacar/.venv/bin/python /var/www/dacar/manage.py collect_server_metrics
```

Пример systemd service (не установлен автоматически). Пользователь обязан
совпадать с непривилегированным пользователем приложения; имя `dacar` здесь
пример, его создание/переход с root — отдельное согласованное изменение.

```ini
[Unit]
Description=DACAR host metrics snapshot

[Service]
Type=oneshot
User=dacar
Group=www-data
WorkingDirectory=/var/www/dacar
ExecStart=/var/www/dacar/.venv/bin/python manage.py collect_server_metrics
UMask=0077
NoNewPrivileges=true
```

Соответствующий timer:

```ini
[Unit]
Description=DACAR metrics each minute

[Timer]
OnBootSec=1min
OnUnitActiveSec=1min
AccuracySec=5s

[Install]
WantedBy=timers.target
```

Сборщик раз в минуту даёт минутные интервалы; открытая панель добавляет замеры
раз в 10 секунд. После деплоя проверить установленный psutil, collectstatic,
доступ к каталогу runtime и права на API. Изменений production в этой задаче нет.

## Границы

Тревоги сохраняются в отдельной служебной SQLite-базе за 24 часа: база недоступна,
CPU/RAM/диск/Swap выше порогов. В админке мониторинга активные события видны
сразу; кнопка «Включить уведомления» разрешает браузерные уведомления. При
заполненных `TELEGRAM_ALERTS_ENABLED`, `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID` новые события и восстановления также отправляются в Telegram.
Отправка выполняется только при смене состояния и не блокирует мониторинг при
ошибке Telegram. При полном отключении VPS админка недоступна — для этого нужен
внешний uptime.
Внешний uptime, резервные копии, TLS и логирование ошибок — отдельный этап.
Не предоставлять Django root ради мониторинга. При падении VPS админка тоже
недоступна; нужна внешняя проверка. В контейнере счётчики могут отражать хост,
а не лимиты контейнера — для текущего прямого запуска на VPS это не требуется.

## Команды Telegram

В Telegram доступны только безопасные команды чтения:

- `/status` — текущие CPU, RAM, диск, Swap, база данных, uptime и активные тревоги;
- `/alerts` — активные проблемы и время их появления;
- `/history` — диапазоны CPU, RAM и диска за последние 24 часа;
- `/help` — список команд.

В сообщениях также есть inline-кнопки для этих действий. Webhook проверяет
секретный путь, секретный заголовок Telegram и разрешённый `TELEGRAM_CHAT_ID`.
Команды ничего не меняют в базе и не перезапускают сервисы. Отдельный процесс
polling не запускается: Telegram обращается к webhook только после действия
пользователя, а данные читаются из служебной SQLite-истории. Поэтому нагрузка
от команд минимальна; постоянный сбор выполняет уже установленный systemd-
таймер раз в минуту.

Проверка: `python manage.py test config.test_monitoring --noinput`.
Не запускать корневой test_all_features.py против рабочей БД.
